Pattern Router / agent-logic — open design decisions

The three genuine forks flagged in infrastructure.html §3.2 — skill selection, distress ordering, and audit/budget ownership. These are design decisions, not doc wording, for the steering / architecture discussion. Each is written up with the options, trade-offs, a recommendation, and what's needed to settle it. None blocks launch; each is mainly a launch → target migration gated on preview features reaching GA.

Companion to infrastructure.html (§3.1 platform pillars, §3.2 gateway vs agent logic) and decisions-and-rationale.html · capability claims verified against Microsoft Learn, Jun 2026

The through-line — read this first. Several of these look like new decisions but mostly dissolve once you notice that our classify step already runs before the agent and already emits {pattern · topic · purpose · risk}. Distress detection (G2) and pattern tagging for audit (G3) fold into that existing pre-agent call for free; skill selection (G1) is just “which prompt that step injects.” The genuinely open part is the launch → target migration — single agent → Foundry handoff, and confirming the gateway owns budget/audit — gated on preview features reaching GA (D6).

Decision G1

Skill selection — one agent reconfigured, or N agents with handoff

The fork. When the classifier picks a pattern (Decide, Express, …), how does that become a running Foundry agent?

Option A — one agent, skill prompt injected per turn. launch / GA One Foundry prompt agent; each turn we pass the chosen pattern's skill prompt as the instructions (via the Responses API). Pattern becomes a trace attribute.
Pros: simplest; one resource; matches our layer cake (system + classifier + active pattern prompt); skills stay our git-versioned files injected at runtime; prompt-agent GA → launch-safe.
Cons: A/B-ing a skill = versioning the injected prompt, not an agent; all patterns share one trace identity; per-pattern tool scoping (only Decide loads Action APIs) is enforced by us per turn, not structurally.

Option B — N prompt agents (one per pattern) + Foundry connected-agents / handoff. target / preview A Foundry agent per pattern; native handoff transfers between them.
Pros: each pattern is first-class — own instructions, tools, identity, per-agent traces (“Decide agent p95”), versioning, A/B; tool-scoping is structural; handoff maps exactly onto our skill files' handoff_targets frontmatter (transfer_to_express, transfer_to_decide already declared).
Cons: connected-agents/handoff is preview (D6); more resources; cross-agent conversation state; the classify step still picks the entry agent.

Recommendation — phase it. Launch = A (one agent, skill injected per turn, pattern as a trace tag). Target = B once handoff is GA — promote each pattern to its own Foundry agent and use native handoff for the transfers. The skill files already encode handoff_targets, so A→B is natural provided skills stay runtime-injected prompts, not baked into fixed agent definitions. That constraint is the call to lock now.
To decide: confirm prompt agents accept per-request instruction injection (they do, via the Responses API); decide whether per-pattern tool-scoping is worth pulling B forward for Decide (the write path) specifically.
Decision G2

Distress ordering — gate before the agent, or run in parallel

The fork. When does distress detection happen relative to the agent generating a response?

Option A — gate. Detect distress before the agent runs; if distress, short-circuit straight to the Express held-state — the normal pattern agent never generates.
Pros: safest — a student in crisis never receives a retrieve-and-answer response; held-state engages first; no chance the model says the wrong thing.
Cons (apparent): a safety pre-check on every turn, including the ~99% non-distress ones.

Option B — parallel. Run the agent and distress detection concurrently; cancel/replace if distress fires.
Pros: no added latency on normal turns.
Cons: race condition — if generation finishes (or streams tokens) before distress fires, the student may briefly see a normal response; cancellation is fiddly, worse with streaming.

Option C — post-filter. Generate, check output, then suppress. Worst — wasted generation and the student waited for nothing.

Recommendation — gate (A), and note it's nearly free. The usual objection is latency, but our classifier already runs before the agent and already emits risk — so distress detection folds into the existing pre-agent classify call; it is not a separate round-trip. Content Safety (GA, in Foundry) seeds/validates severity. Critical severity (self-harm / immediate danger) hard-gates to request_advisor_handoff with no probe — already in the Express skill.
To decide: confirm the distress classifier is part of the pre-agent classify step (so gating is free); set the severity threshold that hard-gates vs soft-routes; keep this distinct from Prompt Shields' XPIA check on retrieved content (a separate concern).
Decision G3

Audit / budget / identity — what's ours vs Foundry's

The risk. Foundry now provides Entra agent identity, App Insights tracing, and model quota / PTU — which overlap our pattern-tagged audit log, per-student budgets, and identity handling. Left unstated, that's two sources of truth.

Recommendation — name the layering so nothing competes. Our pattern-tagged log is authoritative for analytics + retention (Foundry tracing = operational observability, not a substitute); per-student budget is enforced at our gateway before invoking Foundry (quota/PTU is the platform capacity beneath); student identity is ours and flows into the agent context for RLS, alongside Foundry's agent identity.
To decide: confirm we're not double-paying for observability (agree what each emits to App Insights); confirm student_id propagation into the Foundry agent for RLS on MEMORY / records; confirm the budget decrement happens at the edge (so an over-budget student is stopped before a Foundry call is spent).
None of these blocks launch. The launch path uses the GA subset (one prompt agent, skill injected per turn, distress gated in the pre-agent classify call, our gateway owning budget/audit). G1-B and the wider Hosted-agent move are target state, adopted as Foundry connected-agents / Hosted agents reach GA (D6). Record the recommendations; revisit the target items at their GA.
