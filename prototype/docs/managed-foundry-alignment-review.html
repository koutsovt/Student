Managed-Foundry diagram: alignment review & merged architecture

How the merged architecture was reached. The managed-Foundry infrastructure diagram was read against our reference design (infrastructure.html): the managed-first framing was sound and kept, but as drawn it dropped the intent-assessment tier that is the whole point of replacing Charlie. The merge keeps the Foundry managed platform and restores our differentiators as constructs built inside it. The runtime/provider questions this raised are now settled in D1–D6 — this note records the merged design; the rationale lives in the decisions log and the build-vs-buy review.

Solution-architecture review · reflects D1–D6 · companion to infrastructure.html, decisions-and-rationale.html, duplication-buy-vs-build-review.html

1. Verdict

Built ourselves
The classifier and six-pattern routing, the skills library, the distress/Express held-state path, the personalisation tier, the pattern-tagged analytics, and the MCP → SAP PO action middleware. No managed equivalent.
Bought (now managed)
Foundry Agent Service (D1), Azure AI Search (D2), Prompt Shields (D3) and Model Router (D4) — all GA, in AU East. Plus the Admin Console, Tool Registry UI and named ingestion sources.
Consciously traded
Cross-cloud “any model” freedom, narrowed to the in-region Foundry catalogue (D1). Recorded, not silent — T15 re-scoped, not reversed.
Why the Pattern Router stays ours: the Foundry diagram ran one generic agent with no classifier, so every request took the same retrieve-and-answer path regardless of what the student wanted — that is Charlie's purpose-blindness. So classify-before-answer is the agent's own first step, built by us inside Foundry (as a prompt agent at launch, a Hosted agent as the target). (Model-level routing is now managed via Model Router (D4); the intent classification logic is what has no managed equivalent — and it is the business case.)

Architectural insight behind the merge. Azure AI Foundry is a complete agent platform, not just a model runtime — you build agents, tools, knowledge and memory inside it. So the classifier doesn't disappear and it isn't a separate stack bolted on: it becomes the first step of the agent we build inside Foundry. The agent (1) classifies the turn, (2) selects the matching skill prompt and the per-task model, and (3) proceeds with grounding and tools. Our differentiators — the classify-before-answer logic, the skill library, the SAP PO tools, the governed memory — are the content we author into Foundry's platform constructs; Foundry provides the runtime, scaling, identity, safety and observability.
Framing update (reading the diagram below). This diagram was first drawn with our tier “in front of” and “around” Foundry — the older Foundry-as-model-runtime mental model. The correct model is Foundry-as-platform: the left/right zones show what we author (the agent's logic, tools, knowledge, memory), but they are built inside the Foundry platform as a Hosted agent, Toolbox tools, connected knowledge and a connected governed store — not a separate external stack. Read “in front” as sequence (classify first), not topology.

What changed in the merge (reading the diagram)

  • Pattern Router = the agent's first step, built inside Foundry (left, red box). It classifies the turn, picks the skill prompt and the per-task model, then proceeds with grounding and tools. Built as a prompt agent at launch, a Hosted agent as the target — not a separate external tier. This is the structural fix for purpose-blindness.
  • Skills & pattern-prompt library re-inserted (red band). Six git-versioned skill prompts (four reactive wired at launch; Nudge + Check-in in a follow-up release) feed the agent's per-turn instructions; classifier prompts feed the router. A/B and rollback via Container Apps revisions.
  • Express / distress path restored (right, red boxes). Distress classifier in the router + ltu-wellbeing-mcp + Redis hold state give the in-channel advisor handoff with held conversation state.
  • Personalisation tier expanded (centre-lower, red title). USER profile, bounded sanitised MEMORY, session log, and the pattern-tagged log that powers cohort analytics.
  • Actions route through SAP PO (T18). The write path is ltu-actions-mcp → SAP PO → SIS, not MCP → SIS direct.
  • Scale & residency annotated. KEDA autoscale + census-wave behaviour on our compute; an explicit caveat that on Foundry the scale lever becomes model PTU/quota, and residency is met via a managed model endpoint in Azure AU East.
  • Kept from the Foundry proposal: Foundry Agent Service + Azure AI Search as the managed runtime/grounding, the Admin Console, the Tool Registry UI, and the named ingestion sources. Foundry IQ is preview — designed toward as a follow-up agentic-retrieval enhancement (D6); Azure AI Search (GA) is the grounding default at launch, and no launch-critical path depends on a preview feature.
