Every metric has an owner, a target, and an emission point in the orchestrator.

1. Approach — three layers

Charlie’s telemetry answers “how much did the bot do?”. We need to also answer “did the student get what they came for?” and “is the bot getting smarter?”. Three layers, each with a different audience.

Layer 1 · Parity
Did we replace it cleanly?
Mirrors Watson’s 2023–2026 telemetry so executive comparisons hold. Audience: senior leadership, CDO.
Layer 2 · SLOs
Is it healthy right now?
Per-pattern thresholds for latency, grounding, cost, distress recall. Audience: on-call, platform team.
Layer 3 · Insight
Is it serving students better?
Task completion, self-recovery, cohort outcomes, emerging topics. Audience: Charlie product owner, student experience.
Why this matters now. The 2026 Watson data shows containment up, sentiment down, weak-understanding rising. That contradiction is only legible because we have three years of history. If the new assistant launches without parity metrics, we lose the ability to make that comparison and the business case for the replacement becomes unfalsifiable.

3. Watson-parity metrics Parity

Mirrors the columns in the 2023–2026 IBM Stats workbook so YoY and week-over-week comparisons against Charlie stay valid through cutover. Every metric is also sliceable by the seven span tags — an immediate upgrade over Watson’s aggregate-only reporting.

IDMetricDefinition / targetSourceWhy
M1 Total conversations / week Distinct conversation_id count. Baseline 2026: 1,133 / wk. Orchestrator span: 1 per conversation start Volume baseline; capacity planning
M2 Active users / week Distinct hashed_student_id. Baseline 2026: 956 / wk. Span attribute Reach; demand-side trend
M3 Avg messages per conversation Mean turns/conversation, sliced by pattern. Baseline 2026: 4.77. Per-turn span count grouped by conversation_id Replaces Watson’s flat avg with pattern-aware view (Decide naturally longer than Status-Check)
M4 Weak-understanding rate % turns where classifier confidence < 0.6 or retrieval returns nothing above threshold. Baseline 2026: 14.2% equivalent. Classifier output + retrieval pipeline Direct Watson equivalent; trend signal for knowledge gaps
M5 Coverage % queries served by an in-scope pattern (vs out-of-scope refusal). Baseline 2026: 0.85. Classifier’s topic output + safety subsystem refusals Comparable to Watson coverage; declining trend signals corpus drift
M6 Connect-to-Agent rate % conversations ending in live-chat handoff. Baseline 2026: 47%. outcome=escalated_live_chat Parity with Charlie; but see M17 for the more useful metric
M7 Positive sentiment % % turns with thumbs-up or high-confidence positive in LLM-judge sample. Baseline 2026: 11.7%. User feedback widget + M31 sample Trend comparison; replace generic widget with M25 pattern-specific
M8 Top intents (topic × purpose) Rolling top-20 by week. Watson top-3: Connect-to-Agent, Negative-Feedback, ltu-timetable. topic + purpose aggregation Direct equivalent of Watson top-intents; richer because two-dimensional

4. Per-pattern SLOs SLO

INF12 lists alert names (p95, error rate, cost, DLP) but not thresholds. A single p95 across all six patterns hides the only one that matters: Express. These targets are per-pattern and per-pipeline-stage, and every breach pages on-call.

IDMetricPattern · targetSourceWhy
M9 Time to first token (p95) Express < 1.5s · Status-Check < 2.0s · Inform-and-Act < 3.0s · Decide < 5.0s Span: llm.first_token_ms Express delay = real harm; Decide can take longer because the user expects deliberation
M10 End-to-end turn latency (p95) All patterns < 8.0s; Express < 3.0s Span: turn.duration_ms Catches retrieval / tool-call tail latency that M9 misses
M11 Error rate < 0.5% turns return 5xx or fall back to safety refusal-on-error Span status + safety subsystem Baseline reliability
M12 Distress-classifier recall ≥ 95% on red-team Express set; ≥ 90% on live-sampled audit Risk classifier output vs. judge-labelled sample False negatives = missed wellbeing escalation. Highest-stakes single metric in the system.
M13 Distress-classifier precision ≥ 70% (intentionally generous tradeoff vs recall) Risk classifier output vs. judge-labelled sample Precision lower than recall by design; over-escalation is the safer failure mode
M14 Action API success rate Decide pattern ≥ 98% of lodge_action calls return 2xx within 10s MCP tool-server response codes If SIS is down, the bot must say so — not silently fail
M15 DLP-redaction events < 0.1% turns trigger a PII redaction; spike alert > 1% Safety subsystem (T11) Sudden rise = upstream system leaking PII into prompts
M16 Cost per turn Express < $0.008 · Status-Check < $0.012 · Inform-and-Act < $0.025 · Decide < $0.045 LLMClient (T15) per-call cost + retrieval cost Pattern-specific so the “cheap chitchat funds expensive Decides” pattern is visible
SLO budget approach. Each metric has a 28-day rolling error budget (e.g. 0.5% of turns over 28d may exceed M10). Burn-rate alerts at 2× and 10× budget consumption, per Google SRE convention. Budget exhaustion triggers a feature freeze on the affected pattern’s prompt or skill until the SLO recovers.

5. Outcome & behaviour metrics New

Charlie cannot answer any of the questions in this section. These are the metrics that move the SA story from “the bot is running” to “the bot is working”.

IDMetricDefinition / targetSourceWhy
M17 Task-completion rate % Decide / Inform-and-Act turns where the downstream Action API or verifiable next step succeeded. Target ≥ 85% at launch. MCP tool-server 2xx + outcome tag Honest replacement for Charlie’s “containment”. Containment counts abandons; task-completion counts wins.
M18 Self-recovery rate When turn N is judged unhelpful, % of conversations where turn N+1 lands. Target ≥ 60% at launch, trending up. Judge sample (M31) of consecutive turns Trend line on this chart is the cleanest “is the bot getting smarter” signal we have
M19 Pattern classification accuracy (live) % turns where user does not re-prompt to redirect pattern. Target ≥ 90%. Detect re-prompt heuristic + judge sample PR6 fixtures measure classifier in the lab; this measures it in the wild
M20 Grounded-answer rate % Inform-and-Act / Status-Check turns whose response cites at least one retrieved chunk above relevance threshold. Target ≥ 90%. Retrieval pipeline + response post-check Direct hallucination guardrail; declining rate = corpus or chunking regression
M21 Escalation-reason taxonomy Every escalation tagged: out_of_scope · low_confidence · user_requested · risk_detected · repeat_failure outcome tag with reason sub-attribute Watson’s “Connect to Agent” is one bucket; this answers why the escalation happened
M22 Drop-off intent Last-classified topic + purpose on conversations that end without resolution or escalation. Rolling top-10. Conversation-end span without success outcome Tells you exactly where students hit a wall — uniquely actionable for content / skill improvement
M23 Cost per successful outcome M16 ÷ M17 by pattern. Reframes Decide (expensive but high-value) honestly. Derived Per-student cost is the wrong denominator. Per-win is the honest one.
M24 Emerging-topic detector Weekly cluster of queries with low max-similarity to known topics. Surface top-5 unknown clusters. Embedding-space clustering over unclassified-topic queries Watson can only count known intents. The new architecture can flag unknowns before they become weak-understanding spikes.

6. Feedback capture New

The 2022–23 BI sheet shows 98.3% of negative feedback is uncategorised. A generic 👍/👎 widget is the cause. Replace it with pattern-specific microsurveys delivered in-channel at conversation end.

IDMetricPromptPatternWhy
M25 Did-it-help, pattern-shaped “Did you get what you needed?” (Inform-and-Act)
“Did Charlie help you decide?” (Decide)
“Did Charlie understand how you feel?” (Express)
“Was the update useful?” (Status-Check / Nudge / Check-in) 		All six Pattern-aware questions get pattern-aware answers. Tag-rich feedback by construction.
M26 Friction reason (single-tap) If M25 = no, surface 4 chips: didn’t understand me · wrong answer · couldn’t do the thing · took too long Microsurvey Captures the “Blank” category Watson lost. Four chips = four actionable failure modes.
M27 Free-text comment opt-in Optional, ≤ 280 chars. Always optional, never gating. Microsurvey Qualitative thread feeding emerging-topic detector (M24) and prompt iteration
Survey fatigue guardrail. Microsurvey shown at most once per student per 24h, biased to conversations that look completed (M17 success or natural end). Conversations ending in Express handoff never trigger the survey.

7. Cohort & lifecycle slices New

Every metric above is automatically sliceable by these dimensions. Listed as their own metrics because the slices themselves are the insight — not the aggregate they came from.

IDSliceDefinitionSourceWhy
M28 Cohort cross-tab Every outcome metric by: domestic/international · UG/PG · year-of-study · college hashed_student_id joined to SIS cohort attributes at query time (never persisted) Surfaces underserved cohorts. The international-PG-first-year cell is usually where the bot is weakest.
M29 Lifecycle drift Same query / topic at different week-of-semester. Heatmap topic × week. lifecycle tag (early / mid-late / end) + ISO week “Wellbeing queries spike week 8” insights that Watson smeared into a flat average
M30 First-touch vs returning Per-user conversation index 1 vs > 1. M17 should differ — first-touch usually lower. Derived from hashed_student_id history Distinguishes onboarding pain from habitual-use pain; targets different fixes

8. Continuous quality Quality

Three closed loops that keep the system honest between releases. All three feed the prompt iteration cycle described in PR6.

IDMetricCadence / targetSourceWhy
M31 LLM-judge sample Random 1% of conversations scored daily against pattern-fit rubric (5 dimensions per pattern). Target avg ≥ 4.0 / 5. Async judge job · cheaper model than runtime Continuous quality signal without human-rater bottleneck
M32 Red-team replay Full SEC10 set re-run on every prompt or skill change. Pass = 100% (refusals + safe outputs). CI pipeline Prevents regressions on jailbreaks and off-scope topics — gates merge
M33 Scenario fixture pass rate PR6’s 11 fixtures + ongoing additions. Pass = deterministic match on classifier output + grounded answer + correct action invocation. CI pipeline Closes the gap in PR6 by defining “pass” concretely

10. Launch gating — what blocks go-live

Not every metric needs to be live on day one. Three rings: launch blocking, week-4 follow-up, later release. The launch ring is the minimum to make the parity claim and operate safely.

Launch blocking Launch
17 metrics
M1–M8 (parity), M9–M16 (SLOs), M17 (task completion). Without these we cannot prove parity or operate safely.
Week-4 follow-up Launch
10 metrics
M19–M22 (outcome behaviours), M25–M27 (feedback), M28 (cohort), M31–M33 (quality loops). Need 4 weeks of live traffic to baseline.
Later release Later
6 metrics
M18 (self-recovery), M23 (cost-per-win), M24 (emerging topics), M29–M30 (lifecycle / first-touch). High-value but require tooling investment beyond the launch envelope.
Non-negotiable. M12 (distress recall) is the single hardest gate. The system does not go live until the red-team Express set passes ≥ 95% recall on three consecutive builds. This is the only metric with that strictness because it is the only one where a miss can cause real-world harm.
