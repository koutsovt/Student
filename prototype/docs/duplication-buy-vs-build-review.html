Replicate or duplicate? Build-vs-buy against the managed Microsoft components — and the decisions to present

Azure AI Foundry is a complete agent platform — you build agents, tools, knowledge and memory inside it (Foundry Agent Service, Foundry IQ, Model Router, Azure AI Search, Prompt Shields, managed memory). The question is which parts of our reference design are differentiators we author into the platform, and which are infrastructure we should stop self-hosting and let the platform provide. This note answers that component-by-component, validates the design against requirements using current Microsoft documentation, and sets out six decisions to put to the steering group.

1. The answer in three cards

Both are happening. The job is to author what differentiates us inside the Foundry platform, stop self-hosting what the platform now provides, and make two trade-offs explicitly rather than by default.

Build inside Foundry — genuine differentiators
Pattern-classification logic, the distress / Express held-state path, the skills & pattern-prompt library, the SAP PO action middleware. No managed equivalent — but built inside the Foundry platform (as a Hosted agent, Toolbox tools, a connected governed store), not as a separate stack around it.
Use the platform — stop duplicating
Self-hosted retrieval (→ Azure AI Search), custom prompt-injection defence (→ Prompt Shields), hand-rolled per-task model routing (→ Model Router). All GA, all in Australia East — and all native platform capabilities of Foundry.
Decided / to decide
D1 is now set — Foundry as the managed agent platform (AU East), models configurable via the catalogue + Model Router. Still open: which layer owns memory (D5).
The one finding that reframes the alignment review: its central premise — “Foundry has no classifier or routing, so we must build it all in front” — is now partially out of date. Microsoft shipped Model Router (GA, model-level classify-and-route) and connected-agent / handoff orchestration (preview, behaviour-level routing). Our intent-classification logic is still ours to own — but the routing plumbing is now a managed pattern we should not hand-roll.

4. Requirements validation — what current docs confirm and contradict

Checked against Microsoft Learn, doc dates May 2026. Three findings are sharp enough to act on before committing; one is a standing caveat.

Finding 1 — unrestricted model choice + Australian residency + the managed runtime are mutually exclusive today. The reference design wants any-model / provider freedom (T15) with hard AU residency (T17). But some managed-catalogue models run only outside Australia (US / EU regions) and some need an Enterprise / MCA-E subscription — not Australia East. So “any model, in-region, on the managed runtime” cannot all hold; the in-region configurable set is a subset of the catalogue. This is the trilemma in §5 and decision D1.
Finding 2 — an in-region baseline model retires in Australia East on 3 June 2026. If D1 lands on the managed in-region path, a current baseline model is about to retire in-region with its successor not yet confirmed for AU East. Confirm the replacement before committing the managed path.
Finding 3 — PTU is a cap, not a capacity guarantee. Microsoft warns a region/model can “sell out”. On the managed path the scale lever becomes model PTU/quota — exactly when every student logs in at census. Reserve AU East PTU ahead of census; do not assume availability.
Standing caveat — the most attractive managed pieces are preview. Foundry IQ, long-term memory, multi-agent orchestration and wider-catalogue model routing are all preview. Design toward them; treat them as “expected at or after launch”, not guaranteed-GA foundations. (See the maturity strip below.)

5. The decision that gates the rest — the residency trilemma

Three things we want at once. Today you can have any two. The pairing you drop determines the runtime, whether Model Router applies, and whether the stakeholder “not locked in” promise survives.

The architect's resolution: decouple the runtime fork from the component buys. The trilemma only bites the runtime choice (Agent Service vs our LLMClient orchestrator). The managed components that cut our biggest duplication — Azure AI Search, Prompt Shields, Content Safety — are GA, available in Australia East, and adoptable either way. So: adopt those now (D2–D4), and treat D1 as the one genuine fork, not an all-or-nothing “Foundry or not” bet.
Decision taken — the right-hand edge. The runtime goes to Foundry-managed (Australia East), with models kept configurable via the Foundry catalogue + Model Router (selection retained as config, not code). This accepts the residency + managed runtime pairing: the configurable set at launch is whatever the managed platform offers in the Australian region, and unrestricted cross-cloud / any-model choice is dropped (some catalogue models are out-of-region only). T15 is therefore re-scoped — portability narrows from cross-cloud to within the in-region catalogue — not fully reversed. Keeping an out-of-region model in scope would be a side path via a sovereign endpoint (e.g. Sydney) outside the managed runtime. Confirm the in-region model retirement successor (3 June) before it becomes the baseline.

Decision D1 — the gating decision

Model provider & data residency

Decided · direction setHard constraint · T17Activates D4

Context. The design is provider-agnostic with no fixed model (T15), and the stakeholder briefing sells “not locked in”. T17 makes Australian residency non-negotiable for student data. Today, some managed-catalogue models run only in US / EU regions and some need Enterprise/MCA-E — so unrestricted model choice + residency + the managed runtime cannot all hold (§5).

Option A — self-managed runtime, any model via a sovereign endpoint (e.g. Bedrock Sydney), keep LLMClient. Viable. Preserves unrestricted model freedom, provider-agnosticism and residency. We own the orchestrator and retrieval. Forgoes Foundry-managed runtime, IQ and Model Router.

Option B — managed runtime on Foundry, in-region catalogue (Australia East). Viable. Gains managed runtime, Model Router, Foundry IQ, integrated Prompt Shields. Narrows model choice to the in-region catalogue (re-scopes provider-agnosticism); requires confirming the in-region model retirement successor (Finding 2).

Option C — an out-of-region-only catalogue model on the managed runtime. Rejected. US / EU regions only → breaks T17 for student data.

Decision taken — fully-managed runtime, configurable models (refined Option B). Adopt Foundry Agent Service in Australia East as the runtime. Keep models configurable as a first-class config concern — multiple model deployments selected per task/pattern, with Model Router (D4) for cost/quality — so model choice stays config, not code; no model is named in code. T15 is re-scoped, not reversed: portability narrows from cross-cloud to within the Foundry catalogue; record this re-scope explicitly. Residency caveat on record: under AU-East residency the configurable set at launch is whatever the managed platform offers in-region — an out-of-region-only model would be a side path via a sovereign endpoint (e.g. Sydney) outside the managed runtime (Option C stays rejected, T17). Action: confirm the in-region model retirement successor (3 June) before it becomes the baseline. Revisit out-of-region models if/when they reach Australia East.
Decision D2

Knowledge retrieval — managed vs self-hosted

ProposedBiggest duplicationGA · AU East

Context. The reference design self-hosts Docling + LlamaIndex + pgvector + ParadeDB BM25 + BGE reranker. Azure AI Search (GA, Australia East) provides vector + hybrid + semantic ranking as a managed service; Foundry IQ (preview) adds agentic retrieval over it.

Trade-off. Self-host gives provider-neutrality and finer control of chunking/rerank; managed removes the most operationally heavy subsystem we'd otherwise run (embedding jobs, index maintenance, reranker hosting, scaling).

Recommended: Azure AI Search as the default retrieval layer. Retire the self-hosted pipeline unless a measured retrieval-quality gap justifies keeping it. Adoptable regardless of D1. Hold Foundry IQ as a “later” enhancement (preview).
Decision D3

Prompt-injection defence — Prompt Shields vs custom

ProposedGA

Context. SEC6/SEC7 specify custom canary tokens + content validation + provenance. Prompt Shields (GA) covers both direct jailbreak and indirect / cross-prompt (XPIA) injection from retrieved content — exactly our two threat vectors.

Recommended: adopt Prompt Shields as the primary control. Keep structural separators in the system prompt as defence-in-depth; retire the bespoke canary/validation as the load-bearing mechanism. Adoptable regardless of D1.
Decision D4

Per-task model routing — Model Router vs hand-rolled selector

Active · D1 set the pathGA for core models

Context. T16 hand-rolls per-task model assignment (cheap model to classify, stronger to answer). Model Router (GA for the platform's core models) does this as a managed classifier with Cost/Quality/Balanced modes and failover. D1 put us on the managed model path, so Model Router is the natural mechanism for “configurable models.”

Adopt Model Router as the per-task selection mechanism — its Cost/Quality/Balanced modes replace the hand-rolled T16 selector. Keep a thin per-pattern model-selection config above it so model choice stays explicit, auditable, and portable as the in-region catalogue expands. This is how “fully managed” and “models configurable” coexist. Region caveat (verified Jun 2026): Model Router currently deploys only in East US 2 / Sweden Central, not AU East — so at launch use direct in-region model deployments + the config layer, and adopt managed Model Router when it reaches AU East (T17).
Decision D5

Memory ownership — our governed tier vs Foundry managed memory

ProposedResolves an open edge

Context. The alignment review left “memory ownership overlap” unresolved — two layers both want to manage memory. Foundry now offers managed threads (GA) and a long-term per-user memory tool (preview). Our tier is bounded (~800 tok), sanitised on write, RLS-enforced, and residency-controlled.

Trade-off. Managed memory removes a store we maintain; our tier guarantees sanitisation, bounding, residency and a single source of truth the analytics log depends on.

Recommended: we own memory as the system of record. Use managed threads for in-session state if on Agent Service, but keep the governed MEMORY tier authoritative. Managed long-term memory is preview anyway — revisit at GA as a possible simplification.
Decision D6

Dependency on preview features

ProposedPolicy

Context. The merged architecture leans on Foundry IQ, long-term memory, multi-agent orchestration and wider-catalogue model routing — all preview.

Recommended policy: launch-critical paths depend only on GA features. Preview features are designed toward and shipped as “later / follow-up” enhancements, each with a GA fallback. No preview feature sits on the safety, residency or write paths at launch.

7. Recommended path — one slide

  • Adopt the GA managed components now — Azure AI Search (D2), Prompt Shields (D3), Content Safety severity (seeds the distress classifier). All AU-East-safe, all cut real duplication, all independent of the runtime fork.
  • Keep building our differentiators — pattern-classification logic, the distress / Express held-state path, the skills library, SAP PO action middleware, the pattern-tagged analytics log. No managed equivalent.
  • D1 decided — fully-managed Foundry runtime (AU East), models configurable via the catalogue + Model Router (D4). In-region catalogue at launch, no model fixed in code; T15 re-scoped from cross-cloud to within-catalogue (record the re-scope); out-of-region models return to scope only if they reach AU East, else as a sovereign-endpoint side path. Confirm the in-region model retirement successor (3 June).
  • We own memory (D5); preview stays off launch-critical paths (D6).
  • Correct the alignment review on two points: Model Router / connected-agents now exist (the “Foundry can't route” premise is partly outdated), and “residency met via a managed in-region endpoint” silently forecloses unrestricted model freedom.
