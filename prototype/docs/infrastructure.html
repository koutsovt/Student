1. Topology — the big picture

Public traffic enters at Front Door. Identity is Entra. The agent is built inside Azure AI Foundry — the managed agent platform (AU East, D1), not just a model endpoint: its agent runtime, models, tools, knowledge, memory and safety are all Foundry platform constructs (see §3.1). What stays ours is the content of those constructs — the classify-before-answer logic (PR2), the skill prompts, the SAP PO tool implementations, and the governed memory. We also run supporting services on Container Apps: at launch the classify-before-answer orchestration and the three MCP tool servers (registered into Foundry as tools, §8); knowledge is Azure AI Search connected as grounding (D2); injection / self-harm safety is Prompt Shields + Content Safety (D3). Repositories span Azure-managed (Postgres, Redis, Blob) and LTU systems (SIS via SAP PO). Model calls stay inside the Foundry catalogue in-region — no external model-API egress.

See these components in action — the SSAF use case. This page is the static map. For a worked example that traces one enquiry through the boxes above — including why a single topic (SSAF) routes three different ways by purpose — see the SSAF MVP walkthrough. It is the proposed launch use case: high volume, one back-end system (SIS).

3.1 Inside Azure AI Foundry — the agent platform

Azure AI Foundry is a complete agent platform, not just a model runtime (D1). The agent, its tools, its knowledge and its memory are all built inside Foundry as first-class platform constructs — Foundry hosts, scales, secures, identifies and observes them. What stays ours is the content of those constructs: the classify-before-answer logic, the SAP PO tool implementations, the curated knowledge, and the governed-memory rules. The correct mental model is build-inside, not wrap-around: we are not a separate stack bolted in front of a model endpoint; we are building La Trobe's agent within the Foundry platform, using its pillars below.

8. MCP tool servers

Three MCP (Model Context Protocol) servers run as Container Apps services, internal only — no public endpoint. These are the Tools pillar of the Foundry platform (§3.1): each server is registered into Foundry as a tool (via the tool catalogue / Toolbox), so the Foundry agent discovers and invokes them with managed auth — we don't hand-wire a client. The tool implementations stay ours: SAP PO routing, idempotency and audit have no managed equivalent (D1). Hosting them as standalone MCP servers on Container Apps is Microsoft's documented first-class pattern (Entra auth, managed identity, scale-to-zero); the platform-managed dynamic-sessions MCP runs only Python/shell, so it's not a fit for typed LTU tools. CLI-binary tools (subprocess) were considered and rejected per T19 — connection lifecycle against SAP PO and Postgres at census spikes, and the loss of a per-tool auth boundary.

ServerShapeTools exposedDownstreamWhy
ltu-records-mcp Build Azure records_lookup · check_eligibility SAP PO → SIS read path. Status-Check and Decide eligibility queries.
ltu-actions-mcp Build Azure lodge_action (defer · withdraw · transfer · change-load · special-consid’n) SAP PO → SIS write path. Decide pattern Action API calls.
ltu-wellbeing-mcp Build Azure request_advisor_handoff · log_distress_signal Contact-centre platform (advisor routing) + Redis hold state. Express pattern escalation path.
retrieve_knowledge is NOT one of our MCP servers. Knowledge grounding is managed Azure AI Search (D2), surfaced to the Foundry agent as its retrieval source — not a self-hosted pipeline we run. Foundry IQ (preview) is the “later” agentic-retrieval layer over the same index. Our three MCP servers cover only the LTU system-of-record calls (records, actions, wellbeing).
Follow-up release: ltu-outbound-mcp. Nudge and Check-in patterns use send_outbound_message (email · LMS · SMS). A fourth MCP server (ltu-outbound-mcp) will wrap this when the proactive patterns ship. Not needed for the reactive launch baseline.

12. Resilience & DR

Single-region (Australia East) at launch. Geo-redundant Blob for durability. PITR on Postgres for 35 days.

Backup & recovery

  • Postgres — automated daily backups; point-in-time recovery to 35 days; geo-redundant backup storage.
  • Blob — geo-redundant storage; versioning enabled on Knowledge corpus container.
  • Redis — cache; no backup required. State that matters lives in Postgres.
  • Key Vault — soft-delete + purge protection; geo-redundant by default.
  • Audit log — append-only; daily snapshot to Blob Archive (SEC4).
Capacity, not just recovery — the Foundry PTU caveat. On the managed path the model is a reserved-capacity dependency, not an elastic one. Provisioned Throughput (PTU) is a cap, not a guarantee — Microsoft warns a region/model can “sell out”. The availability risk concentrates on census/deadline days, exactly when every student logs in at once. Open action: size and reserve AU East PTU ahead of census rather than assuming on-demand availability; this is currently flagged but not yet sized. Pairs with the open action to confirm the in-region model retirement successor (3 Jun 2026) before fixing a default (D1).

14. Cost shape

Indicative monthly cost for the production deployment at ~30k students. Big-ticket items: Foundry model consumption (capped by per-student budgets) and the primary database. The router compute scales to zero during quiet periods; the model does not — under D1 it is a reserved-capacity (PTU) or pay-as-you-go line on the managed runtime. Model cost is the most variable line — and the most controllable. Models are configurable within the Foundry catalogue via Model Router (D1 · D4 · T16); no model is named in code. Estimates assume a fast low-cost model for classification and a stronger model for content as the baseline; the configured model and PTU reservation change this line significantly. 15. Scale characteristics

Horizontal (compute)

  • Pattern Router — Container Apps autoscale on HTTP request rate. Scale-to-zero at low traffic; max ~10 replicas raisable.
  • Frontend — Static Web Apps CDN scales globally.
  • Retrieval — Azure AI Search scales as a managed service (replicas + partitions); no self-hosted reranker to scale.
  • Model (the new ceiling) — on the managed path the scale lever is Foundry PTU / quota, not replica count. It is a hard cap that can sell out; reserve AU East PTU ahead of census.

Vertical (data + cache)

  • Postgres — start 2 vCore, scale to 4–8 at semester start. Storage autogrows.
  • Redis — 6 GB Premium at launch; scale up without downtime.
  • Connections — PgBouncer in front of Postgres if connection count climbs.

Anticipated load shapes

  • Steady state — ~50–200 concurrent students; router at 1–2 replicas.
  • Census + deadline waves — 5–10× spike for 2–3 days; router scales to 5–10 replicas and database vCore up — but the binding constraint becomes Foundry model PTU/quota, which must be reserved ahead, not autoscaled. Unmodelled, this is the busiest-day failure mode.
  • Express-pattern surges — handoff held states require advisor availability, not infrastructure scaling. Capacity managed by LTU's contact-centre platform / staff scheduling.
